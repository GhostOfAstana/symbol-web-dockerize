# symbol-web-dockerize

Это небольшая веб-мастерская: пользователь вводит текст, выбирает `standard`, `shadow` или `thinkertoy` и получает надпись из ASCII-символов. Проект создан для изучения HTTP на Go, контейнеризации и наблюдаемости. Монитор читает настоящие показатели Docker, объясняет каждый балл и выводит рейтинг по правилам задания. Для его работы не нужны LLM, токены или внешние Go-библиотеки.

Есть и текстовый помощник из базового `symbol-web`: подсказки, подбор шрифта и творческие варианты. Без настроенного LLM он работает в воспроизводимом демонстрационном режиме. Контейнерные показатели демонстрационными значениями не подменяются.

## Что понадобится

- Go 1.26 или новее — для тестов, запуска без контейнера и сборки CLI-монитора.
- Работающий Docker Engine и Docker CLI — для образа, контейнера и живых показателей.
- Для `scripts/docker-smoke.sh`: Bash, curl и Python 3, уже доступные на GitHub Actions Ubuntu.

Проект не устанавливает программы на компьютер. Сборка Docker использует инструменты внутри официальных образов. Сторонних зависимостей Go нет, поэтому `go.sum` не требуется.

## Быстрый запуск в Docker

```bash
docker image build -f Dockerfile -t symbol-web-docker .
docker container run -p 8080:8080 --detach \
  --name symbol-web-container \
  --label io.tomorrow.project=symbol-web-dockerize \
  symbol-web-docker
```

Откройте <http://localhost:8080>. Форма отправляется на сервер обычным POST и работает при выключенном JavaScript. Скрипты добавляют подсказки, копирование результата и состояния ожидания.

Для запуска с ограничениями ресурсов используйте `make image run`: контейнер получает 128 МиБ памяти, один CPU, предел процессов, файловую систему только для чтения и запуск без дополнительных Linux capabilities. Порт можно изменить: `make run PORT=8081`. Не запускайте одновременно второй контейнер с тем же именем; для него задайте `CONTAINER=другое-имя`.

Проверка образа и файлов из ТЗ:

```bash
docker images
docker ps -a
docker exec -it symbol-web-container /bin/bash
ls -l /app
exit
```

`/app` содержит исполняемые `server` и `health-monitor`, каталоги `static`, `templates` и три файла шрифтов. Пользователь `app` имеет UID 10001. Ресурсы также встроены в сервер через `embed`, поэтому бинарник не зависит от текущего рабочего каталога.

## Запуск и тесты без Docker

```bash
go run ./cmd/server
go test ./...
go test -race ./...
go vet ./...
```

По умолчанию сервер слушает `:8080`. Чтобы сменить адрес: `ADDR=127.0.0.1:8081 go run ./cmd/server`. В обычном локальном режиме создание надписей, HTTP healthcheck, подбор шрифта и mock-помощник доступны без Docker.

Код использует ограничение тела формы 32 КиБ, текста 4096 байт и результата 1 МиБ. Одновременно создаются до восьми надписей; при перегрузке сервер отвечает 503 с `Retry-After: 1`. В контейнере задан мягкий предел памяти Go `GOMEMLIMIT=96MiB`, согласованный с лимитом контейнера 128 МиБ из Makefile. Разрешены печатные ASCII-символы, LF, CRLF и буквальная последовательность `\n`. Кириллица и табуляция отсутствуют в учебных шрифтах, поэтому сервер объясняет ошибку с HTTP 400. Это ограничение алфавита шрифта, а не интерфейса: сам интерфейс и документация на русском.

## Монитор настоящего контейнера

Монитор запускается на Docker-хосте, где уже есть CLI и права доступа к daemon:

```bash
go build -o health-monitor ./cmd/health-monitor
./health-monitor symbol-web-container
./health-monitor --json symbol-web-container
```

Он вызывает `docker container inspect --format '{{json .}}' -- <имя>` и `docker stats --no-stream --format '{{json .}}' -- <имя>`. Аргументы передаются прямо процессу, без shell. Из `inspect` берутся `State.StartedAt`, `State.Status`, `State.Running` и `RestartCount`; из `stats` — `MemPerc` и `CPUPerc`. От времени запуска вычитается текущее время хоста. Поэтому системные часы Docker-хоста и монитора должны быть согласованы.

Весь сбор ограничен восемью секундами. Контейнер не найден, остановлен, CLI отсутствует, daemon недоступен, время запуска некорректно или JSON повреждён — монитор завершится с объяснением и ненулевым кодом. Здоровый отчёт вместо ошибки не создаётся. CPU может быть больше 100% на нескольких ядрах; это допустимое значение, получающее ноль баллов по заданной таблице.

### Правила оценки

Интервалы процентов трактуются непрерывно: «50–74» означает `50 <= x < 75`, «75–89» — `75 <= x < 90`. Значение 74,9% не попадает в зазор.

| Показатель | 25 баллов | 15 баллов | 5 баллов | 0 баллов |
| --- | --- | --- | --- | --- |
| Память и CPU | `< 50%` | `[50; 75)%` | `[75; 90)%` | `>= 90%` |
| Перезапуски | `0` | `1–2` | `3–5` | `> 5` |
| Время работы | `>= 3600 с` | `[600; 3600) с` | `[60; 600) с` | `< 60 с` |

Сумма четырёх оценок даёт результат 0–100. Рейтинг: 90–100 → 5 звёзд, 80–89 → 4, 70–79 → 3, 60–69 → 2, ниже 60 → 1. Строки рейтинга в JSON сохранены на английском точно по формату ТЗ.

Примеры из аудита:

- 8,8% памяти, 2,3% CPU, 0 перезапусков и 2 ч 34 мин → `25 + 25 + 25 + 25 = 100`, 5 звёзд.
- 82% памяти, 60% CPU, 3 перезапуска и 5 мин → `5 + 15 + 5 + 5 = 30`, 1 звезда.
- Только что запущенный контейнер с низкой нагрузкой и без перезапусков → 75 баллов: uptime ещё не заработал свои 25. Это прямое следствие ТЗ.

### HTTP-монитор

`GET /health-monitor` предусмотрен для сервера на Docker-хосте. Для включения явно задайте контейнер:

```bash
MONITOR_CONTAINER=symbol-web-container ADDR=127.0.0.1:8081 go run ./cmd/server
curl http://localhost:8081/health-monitor
```

Без `MONITOR_CONTAINER` ответ — HTTP 503 с понятным сообщением. Обычный контейнер приложения не получает Docker socket и Docker CLI: у него остаётся самостоятельный host-монитор. Для аудита достаточно CLI, как разрешает ТЗ. Если HTTP-монитор включён, одновременно выполняется один сбор, остальные запросы получают 503 и `Retry-After: 2`. Это ограничивает число процессов Docker при всплеске запросов. Точка `/healthz` проверяет сам HTTP-сервер и не зависит от доступности Docker.

## Линтер Dockerfile — бонус

```bash
./health-monitor --lint Dockerfile
# либо
make lint
```

Линтер проверяет четыре правила: несколько `FROM`, образы Alpine или Slim, не больше пяти `RUN` и соседний `.dockerignore`. Для каждого выводит `PASS`/`FAIL` и ожидаемую пользу. Путь к `.dockerignore` определяется относительно проверяемого Dockerfile, а не текущей папки. Ничего не исправляет автоматически. Успех всех проверок даёт код 0, замечания — 1, неверные аргументы — 2. Это небольшой учебный анализатор, а не замена полному парсеру Dockerfile или сканеру уязвимостей.

## Метаданные и очистка

Образ содержит OCI-метки названия, описания, исходников и версии. Образ и контейнеры из Makefile помечены `io.tomorrow.project=symbol-web-dockerize`.

```bash
make stop
make clean
```

`make clean` удаляет остановленные контейнеры проекта и его неиспользуемые образы по этой метке. Работающие контейнеры и объекты других проектов не затрагиваются. Контейнер, созданный вручную без проектной метки, удалите явно: `docker container rm symbol-web-container`. Для удаления образа после контейнера: `docker image rm symbol-web-docker`. Общий `docker system prune` не вызывается.

## Текстовый помощник

Без `LLM_BASE_URL` действует mock: детерминированные подсказки и вариации. `/api/recommend-banner` всегда применяет правила к свойствам текста, без сетевой модели. Сетевые ответы проверяются, а ограниченный кеш живёт пять минут и хранит не более 256 ключей.

Для уже работающего Ollama задайте окружение перед запуском:

```bash
LLM_BASE_URL=http://127.0.0.1:11434 LLM_MODEL=имя-уже-установленной-модели go run ./cmd/server
```

Название модели не зашито в код. `LLM_PROVIDER=ollama` используется по умолчанию; `LLM_PROVIDER=openai` выбирает OpenAI-совместимый протокол. Для него при необходимости задаётся `LLM_API_KEY`. Данные `.env.example` — образец: сервер не подгружает `.env` автоматически. Не передавайте секреты в Dockerfile и не коммитьте `.env`. В Docker URL `127.0.0.1` обозначает сам контейнер; адрес внешнего backend должен быть доступен из его сети. Сетевой вызов ограничен десятью секундами; при отказе пользователь получает HTTP 503, а генератор надписей продолжает работать.

## HTTP-маршруты

| Метод и путь | Назначение |
| --- | --- |
| `GET /` | Русская HTML-форма |
| `POST /symbol-art` | Поля формы `text`, `banner`; HTML-результат |
| `GET /static/css/style.css` | Стили |
| `GET /static/js/script.js` | Обратная связь и HTTP-монитор |
| `GET /static/js/text-assist.js` | Текстовый помощник |
| `GET /healthz` | HTTP 200, `{"status":"ok"}` |
| `GET /health-monitor` | Живой JSON-отчёт, если монитор настроен |
| `POST /api/suggest` | JSON `{"text":"Hello"}`, подсказки |
| `POST /api/recommend-banner` | JSON с текстом, выбор шрифта и причина |
| `POST /api/variations` | JSON с текстом, варианты надписи |

Неизвестный адрес даёт 404, неподходящий метод — 405, некорректная форма — 400, слишком большое тело — 413. HTML формируется через `html/template`: пользовательский текст экранируется. Для ошибок сохраняется та же визуальная структура. В интерфейсе есть видимый фокус, подписи полей, состояния ожидания, область результата с горизонтальной прокруткой и учёт `prefers-reduced-motion`.
