# Ответы и разбор вопросов аудитора

Материал объясняет фактическую реализацию: вопросы из ТЗ, основные решения, пограничные случаи и проверяемые ограничения. Ответы полезно сверять с кодом и воспроизводимыми примерами.

## Назначение и путь запроса

**Зачем нужен проект?** Чтобы превратить консольное ASCII-искусство в веб-приложение, упаковать его в воспроизводимый контейнер и получать объяснимую оценку по настоящим метрикам Docker.

**Что происходит после нажатия «Создать надпись»?** Браузер отправляет POST `/symbol-art` с `text` и `banner`. Handler ограничивает тело, проверяет формат формы, передаёт значения генератору. Генератор выбирает заранее проверенный шрифт и собирает восемь строк для каждой непустой строки текста. Handler вставляет результат в экранирующий HTML-шаблон внутри `<pre>`.

**Почему форма работает без JavaScript?** У неё есть обычные `method="post"`, `action="/symbol-art"` и именованные поля. Скрипт добавляет состояния ожидания и помощника, но HTTP-генерация от него не зависит.

**Почему нельзя ввести кириллицу?** В официальных файлах заданы только ASCII-коды 32–126. Неизвестный символ не заменяется похожим: сервер возвращает 400, чтобы результат был предсказуемым.

**Как сохраняются пробелы и переносы?** Шрифтовые строки не обрезаются. Вывод находится в `<pre>` с моноширинным шрифтом и горизонтальной прокруткой. CRLF нормализуется в LF. Пустая строка даёт перевод строки, а не восемь пустых строк.

**Что будет при повреждённом файле шрифта?** Проверка структуры выполняется в `ascii.New` при запуске. Сервер не начинает принимать запросы с некорректными ресурсами.

## Docker и устройство образа

**Образ и контейнер — в чём разница?** Образ — файловый шаблон приложения и его настроек. Контейнер — запущенный экземпляр образа с собственным процессом, именем, портом и ограничениями ресурсов.

**Почему Dockerfile многоэтапный?** Первый этап содержит Go, исходники и тесты. Второй получает готовые бинарники и ресурсы. Компилятор и сборочный кеш в рабочий образ не копируются.

**Зачем Alpine?** Небольшая база уменьшает итоговый размер. Для аудиторского входа через `/bin/bash` добавлен Bash; сертификаты нужны для HTTPS-подключения текстового помощника.

**Почему запускается бинарник, а не `go run`?** Компиляция уже завершена на этапе сборки. Рабочему контейнеру не нужны компилятор, сеть загрузки модулей и исходники для запуска.

**Зачем UID 10001?** Процесс не требует привилегий root и слушает непривилегированный порт 8080. Отдельный пользователь уменьшает полномочия приложения внутри контейнера.

**Что означает `-p 8080:8080`?** Левый порт принадлежит хосту, правый — контейнеру. `EXPOSE 8080` документирует порт, но не публикует его сам.

**Какие метаданные добавлены?** OCI title, description, source, version и проектная метка. Это позволяет определить происхождение образа и отбирать объекты проекта при очистке.

**Почему ресурсы одновременно встроены и лежат в `/app`?** `embed` делает бинарник независимым от рабочей папки. Небольшие текстовые ресурсы оставлены в образе для проверки структуры файлов по ТЗ.

**Зачем HEALTHCHECK?** `/app/server --healthcheck` отправляет короткий HTTP-запрос на `/healthz`. Это проверка доступности приложения, отдельная от числовой оценки CPU/памяти. HEALTHCHECK сам по себе не перезапускает нездоровый контейнер.

**Что происходит при SIGTERM?** Сервер прекращает принимать новые соединения и ждёт текущие до пяти секунд. Если времени не хватает, соединения закрываются. Процесс является entrypoint напрямую, поэтому сигнал не теряется в промежуточном shell.

## Настоящие показатели

**Какая команда даёт каждый показатель?** `docker container inspect` даёт `State.StartedAt` и `RestartCount`. Разница между текущим временем и `StartedAt` — uptime. `docker stats --no-stream` даёт `MemPerc` и `CPUPerc`. JSON-формат исключает разбор визуальной таблицы.

**Может ли монитор придумать цифры при ошибке Docker?** Нет. Статический пример используется только в unit-тестах. Рабочий сбор требует корректных inspect/stats, запущенного контейнера, валидного времени и процентов.

**Что если контейнер не существует или daemon выключен?** CLI завершает работу с кодом 1 и сообщением об ошибке. HTTP-монитор возвращает 503; сам веб-сервер продолжает обслуживать генератор.

**Что если контейнер остановлен?** `State.Running=false` или статус не `running` вызывают ошибку. Нулевая загрузка остановленного контейнера не должна выглядеть здоровьем.

**Почему CPU может превысить 100%?** На нескольких ядрах Docker суммирует загрузку процессора. Такое значение допустимо, но по учебной таблице при `>=90%` получает ноль баллов.

**Память считается как RSS?** Монитор использует именно `MemPerc` Docker CLI, как требует ТЗ. Представление CLI может учитывать платформенные поправки, например файловый кеш. Код не выдаёт этот показатель за универсальный RSS.

**Насколько атомарны данные?** Inspect и stats выполняются последовательно. Это не транзакционный снимок: контейнер может изменить состояние между командами. При ошибке сбора отчёт не выдаётся. Для учебного моментального отчёта этого достаточно; история и тренды не заявляются.

**Зачем общий таймаут?** Недоступный daemon не должен удерживать запрос бесконечно. Контекст восемь секунд охватывает обе команды; процесс Docker получает отмену. Вывод ограничен 64 КиБ, stderr — 8 КиБ.

**Как исключена подстановка shell-команд в имя?** Имя сначала проверяется разрешённым шаблоном, затем передаётся отдельным аргументом `exec.CommandContext`. Shell не вызывается; `--` отделяет имя от флагов.

## Баллы и звёзды

**Как считаются баллы?** Каждый из четырёх показателей получает 0, 5, 15 или 25 баллов. Четыре оценки складываются без дополнительного веса и нормализации.

**Как трактуется память 74,9%?** Это меньше 75%, поэтому 15 баллов. Пороговые интервалы непрерывны: `<50`, `<75`, `<90`, иначе 0. Ровно 50 → 15, ровно 75 → 5, ровно 90 → 0.

**Сколько дают ровно 60, 600 и 3600 секунд?** Соответственно 5, 15 и 25 баллов. Возраст проверяется по секундам без преждевременного округления минут.

**Посчитайте пример: 82% памяти, 60% CPU, 3 перезапуска, 5 минут.** Память 5, CPU 15, перезапуски 5, uptime 5. Итого 30/100, `1 star (Critical)`.

**Почему звёзды выводятся из суммы?** Сначала вычисляется одна сумма, затем одна функция `Rating` выбирает интервал. Нельзя отдельно выставить пять звёзд контейнеру с 30 баллами.

**Почему новый спокойный контейнер не даёт 100?** До первой минуты uptime получает 0. Остальные три показателя могут получить по 25: всего 75. Таблица из ТЗ оценивает ещё и длительность работы.

**Может ли рейтинг измениться без смены памяти?** Да: вырос uptime, CPU либо число перезапусков. Это оценка четырёх показателей, а не только памяти.

**Является ли этот рейтинг промышленной гарантией здоровья?** Нет. Это объяснимая учебная модель. Она не проверяет корректность бизнес-логики, задержки запросов, диск или сетевые зависимости. Для доступности HTTP отдельно есть `/healthz`.

## Линтер и очистка

**Какие правила проверяет бонусный линтер?** Два или больше `FROM`, базы Alpine/Slim, максимум пять `RUN`, наличие `.dockerignore` рядом с проверяемым Dockerfile. Для каждого правила он показывает пользу.

**Считает ли строку продолжения отдельным RUN?** Нет. Продолжение после `\` относится к предыдущей инструкции; команды внутри одной `RUN` не становятся новыми инструкциями.

**Может ли линтер изменить Dockerfile?** Нет, он только открывает и читает его. Это дополнительно проверяется тестом сравнения байтов до и после.

**Это полный Dockerfile-парсер?** Нет. Поддерживаются обычные инструкции и продолжения строк для четырёх учебных правил. Сложные heredoc, динамические ARG в `FROM` и семантическая проверка существования образов находятся вне заявленного назначения.

**Почему не запускается общий `docker system prune`?** Он может затронуть чужие неиспользуемые объекты. Makefile ограничивает удаление проектной меткой. Запущенные контейнеры не удаляются prune-командой; сначала нужен `make stop`.

**Что такое мусор в данном проекте?** Остановленные контейнеры и неиспользуемые образы, помеченные проектом. Build cache и volumes других проектов не очищаются.

## HTTP, устойчивость и тесты

**Какие ошибки предусмотрены?** 400 для некорректного текста/формы, 413 для слишком большого тела, 404 для неизвестного пути, 405 для неправильного метода, 503 для недоступного монитора или LLM. Ошибка подготовки шаблона при запуске останавливает старт.

**Как предотвращается XSS?** Результат и исходный ввод передаются как строки в `html/template`. В JS ответы показываются через `textContent`. Нет преобразования пользовательской строки в доверенный HTML.

**Почему один одновременный HTTP-сбор Docker?** Stats сам делает выборку и может занимать время. Ограничение не позволяет большому числу запросов породить столько же subprocess. Генерация ASCII при этом независима.

**Что проверяется в unit-тестах?** Обе контрольные оценки из ТЗ, все границы баллов и рейтинга, NaN/Inf/отрицательные значения, контракты Docker CLI, повреждённые ответы, неизвестные имена, неподдерживаемые методы, пределы тела, XSS, конкурентная генерация и занятый монитор.

**Что проверяет `-race`?** Инструмент ищет гонки памяти в реально выполненных конкурентных сценариях. Он не доказывает отсутствие всех возможных ошибок, но проверяет совместное использование генератора, кеша и ограничителя на наших сценариях.

**Что проверяет fuzzing?** Генератор тестов меняет входные значения. Для допустимых метрик сохраняются инварианты: сумма 0–100, рейтинг соответствует сумме, JSON сериализуется. Другой fuzz-тест подаёт произвольные Docker JSON и проценты, проверяя отсутствие panic.

**Чем unit-тесты отличаются от живого Docker smoke?** Unit-тесты проверяют алгоритмы и ошибки на управляемых данных. Smoke реально строит образ, запускает контейнер, проверяет HTTP, файлы, labels и CLI-показатели, затем удаляет свои объекты. Пройденные unit-тесты не означают автоматически пройденный smoke.

**Почему нет `go.sum`?** В `go.mod` нет сторонних модулей. Все пакеты принадлежат стандартной библиотеке Go; Docker CLI вызывается как уже установленная внешняя программа.

**Как mock выбирается у текстового помощника?** Пустой `LLM_BASE_URL` включает mock. При URL требуется `LLM_MODEL`; данные читаются из окружения. Ошибка реального backend не маскируется успешным mock-ответом.

**Почему Docker socket не монтируется в приложение?** Для предусмотренной проверки достаточно CLI на Docker-хосте. Приложение не нуждается в возможностях управления Docker daemon. Если нужен HTTP-отчёт, сервер можно запустить на хосте с явным `MONITOR_CONTAINER`.
