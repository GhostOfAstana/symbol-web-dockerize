# Как проверять проект

## Локальные алгоритмы и HTTP

```bash
go test ./...
go test -race -cover ./...
go vet ./...
test -z "$(gofmt -l .)"
go run ./cmd/health-monitor --lint Dockerfile
go test ./internal/monitor -run '^$' -fuzz FuzzScore -fuzztime 10s
go test ./internal/monitor -run '^$' -fuzz FuzzDockerJSON -fuzztime 10s
go test ./internal/ascii -run '^$' -fuzz '^FuzzGenerate$' -fuzztime 10s
```

Go допускает один выбранный fuzz-target за запуск. Unit-тестам Docker daemon не нужен: проверяются чистые алгоритмы и управляемые ошибочные ответы. Рабочий `Collect` использует настоящий CLI; тестовые данные в production-путь не встроены.

Проверяются точные границы процентов, секунд, перезапусков и рейтингов, оба примера аудита, отрицательные значения, NaN/Inf, повреждённый JSON, некорректные имена контейнера, лимиты вывода, лимит формы, неизвестные шрифты, экранирование HTML, одновременно 64 генерации и ограничение параллельного сбора Docker.

## Контейнер целиком

```bash
bash scripts/docker-smoke.sh
```

Скрипт требует уже работающий Docker, Go, Bash, curl и Python 3. Он строит образ из проектного Dockerfile, запускает именованный контейнер на случайном localhost-порту, проверяет три шрифта, static, mock-подсказки, пользователя без root, Bash, ресурсы, labels и настоящий JSON монитора. После остановки проверяется, что монитор возвращает ошибку. Trap удаляет только контейнер и образ данного запуска, в том числе при падении проверки.

Этот тест автоматически выполняется заданием `container` в GitHub Actions. Он создаёт как минимум один реальный образ и контейнер; успешный результат подтверждается журналом конкретного прогона. Число uptime на новом контейнере невелико, поэтому smoke не требует 100 баллов: он проверяет согласованность суммы, рейтинга и фактических полей.

## Ручная проверка аудитора

1. Открыть интерфейс на 375, 768 и 1920 пикселях; форма должна оставаться читаемой, ASCII-вывод прокручивается внутри панели.
2. Пройти страницу клавишей Tab, отправить форму Enter или кнопкой. Фокус виден, подписи полей связаны с вводом.
3. Отправить многострочный текст каждым шрифтом, пустую строку, кириллицу и слишком длинный ввод. Ожидаем либо точный результат, либо понятную ошибку.
4. При выключенном JavaScript создать надпись обычной формой.
5. Запустить CLI против работающего и отсутствующего контейнера, затем против остановленного.
6. Сопоставить поля `inspect`/`stats` с отчётом. Значения динамичны и меняются между вызовами: не требуйте побайтного совпадения двух разных моментов.
7. Проверить --lint на хорошем Dockerfile и копии без `.dockerignore`; исходный файл не должен измениться.
8. Отправить запрос к HTTP-монитору без конфигурации: ожидается 503, при этом `/healthz` и генерация работают.

## Чего проверка не доказывает

Рейтинг из четырёх порогов не гарантирует отсутствие ошибок приложения. Ограниченный fuzzing не перебирает все входы, race detector охватывает выполненные сценарии. Доступность реального LLM зависит от пользовательской конфигурации и отдельно от контейнерных метрик. Наличие CI-файла не подтверждает успешность CI до завершения конкретного запуска.
